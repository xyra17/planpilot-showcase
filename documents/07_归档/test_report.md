## 模块一：验收出题（POST /verify）

### 1. 模块概述

验收出题模块接收用户目标（`goal_id`）及近期打卡记录，由 LLM 生成 3~5 道验收题，覆盖选择题（MCQ）、简答题（SAQ）与反思题（Reflection）三种题型。测试目标：验证题目与目标的相关性、难度梯度合理性、题型分布均衡性及语言表达质量。

### 2. 测试用例设计

黄金数据集构建方式：从真实用户目标库中抽取 15 条目标（5 条学习类、5 条技能类、5 条习惯类），搭配对应近 7 日打卡记录作为输入。人工为每条样本预设：① 期望题型分布（≥1 MCQ + ≥1 SAQ + ≥1 Reflection）；② 关键知识点覆盖清单；③ 难度区间（Easy / Medium / Hard 各至少 1 题）。共 15 个 Case，独立评分取均值。

### 3. 评估指标

| 维度 | 评分方式 | 权重 |
|---|---|---|
| 目标相关性 | LLM Judge 1~5 分，题目是否紧扣目标内容 | 35% |
| 题型覆盖度 | 代码硬比对，三种题型是否均出现 | 25% |
| 难度梯度 | LLM Judge 判断是否包含 Easy/Medium/Hard | 20% |
| 语言清晰度 | LLM Judge 评估表述是否准确无歧义 | 20% |

综合分 = Σ(维度得分 × 权重)，满分 1.0，上线阈值 0.80。

### 4. 测试结果

| 维度 | 均分 |
|---|---|
| 目标相关性 | 0.91 |
| 题型覆盖度 | 0.93（14/15 Case 完全覆盖三题型）|
| 难度梯度 | 0.83 |
| 语言清晰度 | 0.86 |
| **综合得分** | **0.88 / 1.0 ✅** |

15 个 Case 中，1 个因目标描述过短（"学英语"，共 4 字）导致 LLM 仅生成 2 道 MCQ，题型覆盖维度得 0 分，拉低整体均分约 0.02。

### 5. 问题分析 & 优化建议

**主要问题**：目标描述字符数 < 20 时，Prompt 信息量不足，LLM 退化为最保守的题型组合（全 MCQ）。**建议**：在 Prompt 中增加防退化指令（"无论目标描述长短，必须输出三种题型各至少一道"），并对极短目标注入引导文本补充上下文，无需修改核心逻辑。预计修复后覆盖率提升至 ≥0.97。

## 模块二：验收评分（POST /verify/answer）

### 1. 模块概述

验收评分模块接收用户对验收题的作答，由 LLM 对每道题逐一评分（1~5 分）并给出详细反馈，最终汇总为通过/不通过判定。该模块为 P0 级，上线阈值设为 0.85，是整个验收闭环的核心评判环节。

### 2. 测试用例设计

基于模块一生成的题目，人工撰写 3 类标准答案：**满分答案**（期望得 4~5 分）、**部分答案**（期望得 2~3 分）、**错误/空答案**（期望得 1 分）。共 45 组「题目 + 答案 + 期望分值」三元组，构成黄金数据集。通过 Score MAE（模型打分与人工期望分值的绝对误差均值）和 Cohen's Kappa（通过/不通过二元判定一致性）双指标评估。

### 3. 评估指标

| 指标 | 计算方式 | 目标阈值 |
|---|---|---|
| Score MAE | \|LLM分 − 人工期望分\| 均值，满分5分制 | ≤ 0.7 |
| Cohen's Kappa | 通过/不通过判定与人工判定的一致性 κ 值 | ≥ 0.70 |
| 反馈可读性 | LLM Judge 评估反馈文本质量（1~5分） | ≥ 3.5 |
| 综合得分 | 三指标归一化加权（40%+35%+25%） | ≥ 0.85 |

### 4. 测试结果

| 指标 | 结果 |
|---|---|
| Score MAE | 0.52（满分5分制，低于阈值0.7）|
| Cohen's Kappa | 0.74（通过/不通过判定一致性良好）|
| 反馈可读性 | 3.9 / 5.0 |
| **综合得分** | **0.86 / 1.0 ✅** |

满分答案的判定准确率达 97%；错误答案中有 3 例 LLM 给出 2 分（期望 1 分），表现为"过于宽容"偏差，是主要失分来源。

### 5. 问题分析 & 优化建议

**主要问题**：LLM 在评分时存在轻微"宽松偏差"，对明显错误答案给分偏高（2 分而非 1 分）。**建议**：在评分 Prompt 中加入评分锚定示例（Few-shot Calibration），明确展示 1 分（完全错误）与 2 分（有微弱相关性）的区别案例，预计可将 MAE 降至 ≤0.40，Kappa 提升至 ≥0.80。

## 模块三：日报生成（GET /daily-brief）

### 1. 模块概述

日报生成模块综合用户所有活跃目标的近期打卡记录、连续天数（streak）及 AI goal review，生成包含「summary」、「insight」、「recommendedAction」的结构化日报。该模块与 Celery 定时任务深度绑定，每日 7:30 预生成并落库，用户访问时优先读取缓存。

### 2. 测试用例设计

构建 12 个用户状态快照：① 3 个高活跃用户（streak ≥ 7，多目标均有打卡）；② 3 个低活跃用户（streak = 1~2，仅 1 个目标有记录）；③ 3 个停滞用户（3 日无打卡）；④ 3 个新用户（首次打卡当天）。人工为每类状态预设期望输出的关键要素（如低活跃用户的 recommendedAction 应包含激励性语言），构成黄金集。

### 3. 评估指标

| 维度 | 评分方式 | 权重 |
|---|---|---|
| 内容准确性 | LLM Judge：summary 是否与打卡数据一致，无幻觉 | 40% |
| 洞察深度 | LLM Judge：insight 是否有实质性分析（非泛泛而谈）| 30% |
| 行动建议相关性 | LLM Judge：recommendedAction 是否具体可执行 | 20% |
| 结构完整性 | 代码硬比对：三字段是否均存在且非空 | 10% |

### 4. 测试结果

| 维度 | 均分 |
|---|---|
| 内容准确性 | 0.89 |
| 洞察深度 | 0.78 |
| 行动建议相关性 | 0.82 |
| 结构完整性 | 1.00（12/12 Case 结构完整）|
| **综合得分** | **0.83 / 1.0 ✅** |

停滞用户（3日无打卡）场景下，洞察深度得分仅 0.61，LLM 倾向于输出泛化激励语（"坚持就是胜利"），缺乏针对性分析。

### 5. 问题分析 & 优化建议

**主要问题**：无打卡数据时 insight 质量下滑明显，Prompt 未区分"数据丰富"与"数据匮乏"两种路径。**建议**：根据近 3 日打卡数是否为 0 分支 Prompt，为无数据场景提供专用模板（聚焦于"重新激活"而非"分析进展"），预计洞察深度提升 0.10~0.15 分。

## 模块四：宏观规划（POST /macro-plan/{goal_id}）

### 1. 模块概述

宏观规划模块接收目标 ID，结合目标描述、截止日期及用户历史上下文，生成分阶段的里程碑规划（phases），每个 phase 包含名称、时间范围、核心任务列表及成功标准。测试重点在于规划的合理性、时间分配均衡性及与目标实际可达性的匹配程度。

### 2. 测试用例设计

抽取 10 个真实目标（截止期跨度覆盖 1 个月 / 3 个月 / 6 个月 / 1 年四个量级），人工为每个目标撰写参考规划方案，明确标注：① 合理的 phase 数量（时长 1 月对应 2~3 phase，1 年对应 4~6 phase）；② 关键里程碑必须包含的核心任务关键词；③ 时间分配是否均衡（无某 phase 时间段明显过短/过长）。

### 3. 评估指标

| 维度 | 评分方式 | 权重 |
|---|---|---|
| Phase 数量合理性 | 代码比对：phase 数是否在期望范围内 | 20% |
| 里程碑相关性 | LLM Judge：核心任务是否覆盖参考方案关键词 | 40% |
| 时间分配均衡性 | 代码计算：最长/最短 phase 时长比是否 ≤ 3 | 20% |
| 成功标准可测量性 | LLM Judge：成功标准是否具体可量化 | 20% |

### 4. 测试结果

| 维度 | 均分 |
|---|---|
| Phase 数量合理性 | 0.90 |
| 里程碑相关性 | 0.83 |
| 时间分配均衡性 | 0.80 |
| 成功标准可测量性 | 0.77 |
| **综合得分** | **0.82 / 1.0 ✅** |

成功标准可测量性得分最低（0.77），主要表现为 LLM 输出"熟练掌握 X"之类的模糊标准，而非"能够独立完成 X 类型任务 3 例"的可验证标准。

### 5. 问题分析 & 优化建议

**主要问题**：成功标准表述模糊，缺乏量化锚点。**建议**：在 Prompt 中增加成功标准格式约束（"每条成功标准必须包含可观测的行为动词 + 数量/次数/时长等量化指标"），并提供 2~3 个 Few-shot 示例对比"模糊版"与"量化版"差异，预计该维度提升至 ≥0.88。

## 综合结论与后续计划

本次测试完成两轮评测，最终 PlanPilot 全部 6 个 AI 功能模块均达到上线标准。

| 模块 | 初测得分 | 重测得分 | 最终结论 |
|---|---|---|---|
| 验收出题 | 0.88 | — | ✅ 一次通过 |
| 验收评分 | 0.86 | — | ✅ 一次通过 |
| 日报生成 | 0.83 | — | ✅ 一次通过 |
| 宏观规划 | 0.82 | — | ✅ 一次通过 |
| 每日任务推荐 | 0.71 | **0.86** | ✅ 重测通过 |
| 对话规划 | 0.68 | **0.84** | ✅ 重测通过 |

**经验总结**

两个重测模块的核心问题均源于 Prompt 设计缺陷，而非模型能力瓶颈。以下是具体的修改对比。

**模块五：每日任务推荐 — 三处 Prompt 缺陷**

_缺陷一：LLM 没有任何调度依据，导致多目标冲突时平均分配时间_

修改前（原 Prompt 只传入每日时间预算，无目标元信息）：
```
每日学习预算：{budget_mins}分钟

待完成任务（含过期）：
- [id] 任务名 (scheduled:日期, priority:P1, mastery:L2)
...
```

修改后（新增目标截止日期和紧迫度标签）：
```
目标元信息：
- 截止日期：2026-09-01（距今 43 天，紧迫度：中（≤90天））
- 当前水平：beginner
- 每日学习预算：120 分钟

待完成任务（含过期，按 priority 降序排列）：
...
```
同时在规划规则中增加了明确的调度指令："按 priority 降序安排任务；紧迫度为极高/高时，今日任务总时长可上浮至预算的 120%"。LLM 有了可操作的排序依据，不再均分。

_缺陷二：极端时间场景无兜底，导致 1h 预算下输出4个15min小任务_

修改前规则5：`总时长不超过预算，每个任务15-60分钟`

修改后新增规则6：`【极端时间守卫】若预算 < 120 分钟，输出任务数量不超过 2 个，单任务时长不低于 30 分钟`

同时将任务时长下限从15min收紧至30min（规则7）。

_缺陷三：时间约束过于宽松，"不超过预算"给了 LLM 太大的随意空间_

修改前：`总时长不超过预算`（偏差率最高可达30%+）

修改后：`【时间总量约束】总时长必须控制在预算 ±10% 以内（108~132 分钟）`，用具体数字锚定范围，消除模糊空间。

---

**模块六：对话规划 — 两处 Prompt 缺陷 + 一处关键词缺失**

_缺陷一：chat 节点 System Prompt 没有多轮对话维护指令，导致第3轮起丢失前轮确认的目标_

修改前（`nodes/chat.py` _SYSTEM 全文）：
```
你是 PlanPilot，一名专业的 AI 学习规划教练。
帮助用户制定学习计划、跟踪进度、保持学习动力。
回答简洁、友好、有建设性。用中文回复。
你只讨论与学习、规划、目标管理相关的话题。...
当用户询问具体的学习资源、书籍、课程推荐时，使用 web_search 工具搜索最新信息。
```
