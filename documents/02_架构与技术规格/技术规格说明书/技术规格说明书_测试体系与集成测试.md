# 技术实现与架构说明书
## PlanPilot 测试体系与集成测试（2026-07-23）

---

## 0. 概述

PlanPilot 采用两层测试架构：

| 层级 | 位置 | 数据库 | 目标 |
|------|------|--------|------|
| 单元/功能测试 | `backend/tests/` | SQLite in-memory | 快速验证单个路由逻辑，无外部依赖 |
| 集成测试 | `backend/tests/integration/` | 真实 PostgreSQL | 验证完整业务链路，含 pgvector、LLM 调用 |

本文重点说明集成测试体系的设计思路、实现方式与使用方法。

---

## 1. 为什么需要集成测试

### 1.1 单元测试的局限

现有单元测试（`tests/*.py`）使用 SQLite in-memory + per-test 回滚，存在以下盲区：

- **pgvector 无法测试**：SQLite 不支持 `CREATE EXTENSION vector`，向量检索、相似度排序无法覆盖
- **跨表依赖**：Goal → Task → CheckinRecord → Debt 的级联逻辑，SQLite 的 FK 行为与 PostgreSQL 不同
- **真实 LLM 链路**：宏观计划生成、每日简报、掌握度验证涉及真实 DeepSeek API 调用，单元测试全部 mock
- **数据状态积累**：打卡连续天数、学习债务等依赖跨请求的状态积累，in-memory 测试每次回滚无法模拟

### 1.2 集成测试的补充价值

| 能力 | 单元测试 | 集成测试 |
|------|---------|---------|
| 路由参数校验 | ✓ | ✓ |
| 业务逻辑正确性 | ✓ (mock) | ✓ (真实) |
| pgvector 向量检索 | ✗ | ✓ |
| 跨模块状态依赖 | ✗ | ✓ |
| 真实 LLM 输出结构 | ✗ | ✓ |
| 数据持久化验证 | ✗ | ✓ |
| HTML 可读报告 | ✗ | ✓ |

## 3. 核心设计：Session 级共享状态

### 3.1 为什么使用 Session 级 Fixture

集成测试的 55 个测试函数都带有 `scope="session"` 的 fixture。这意味着：

- 整个测试套件只创建**一个**数据库连接、**一个** HTTP client
- 所有测试共享同一个 PostgreSQL 数据库（`planpilot_test`），数据持续累积
- 前序测试写入的数据可以被后续测试读取

对比 `scope="function"`（每个测试独立连接+回滚）：

```
scope=function:  [连接] → 测试A → [回滚] → [连接] → 测试B → [回滚]
scope=session:   [连接] → 测试A → 测试B → 测试C → ... → [结束，数据保留]
```

Session 级的好处：
- 模拟真实用户操作流（注册 → 创建目标 → 打卡 → 生成报告），上下文完整
- 避免重复建连开销，55个测试总耗时约 52 秒
- 数据保留在 `planpilot_test` 库，可事后检查

### 3.2 `shared` Dict：跨测试传递 ID

```python
# conftest.py
@pytest.fixture(scope="session")
def shared():
    state = {}
    yield state
    # 测试结束时写入快照
    snapshot = REPORTS_DIR / "test_data_snapshot.json"
    snapshot.write_text(json.dumps(state, indent=2, ensure_ascii=False))
```

测试文件按编号顺序运行，前序文件将创建的 ID 写入 `shared`，后续文件读取：

```python
# test_02_goals.py
async def test_create_goal_exam(client, auth_headers, shared, seed):
    r = await client.post("/api/v1/goals", json=seed["goals"][0], headers=auth_headers)
    shared["goal_id_1"] = r.json()["id"]  # 写入

# test_04_checkin_debts.py
async def test_checkin_quick_all_done(client, auth_headers, shared, seed):
    goal_id = shared["goal_id_1"]          # 读取
    r = await client.post(f"/api/v1/checkin/{goal_id}", ...)
```

## 4. 数据库引擎替换机制

### 4.1 为什么需要"替换"

后端代码在 `src/database.py` 中定义了全局引擎：

```python
engine = create_async_engine(os.environ["DATABASE_URL"], ...)
AsyncSessionLocal = async_sessionmaker(engine, ...)
```

父级 `tests/conftest.py` 在 import `src.main` 之前就把 engine 替换成了 SQLite（用于单元测试）。集成测试的 `conftest.py` 需要在此之上再替换回 PostgreSQL。

### 4.2 替换顺序

```python
# integration/conftest.py 执行顺序（模块级，import 时立即执行）

# Step 1: 设置环境变量（最高优先级）
os.environ["DATABASE_URL"] = TEST_DB_URL

# Step 2: import src.database（此时模块被首次载入，读取 Step1 的环境变量）
import src.database as _db

# Step 3: 创建 PG 引擎并直接替换模块属性
_PG_ENGINE = create_async_engine(TEST_DB_URL, poolclass=NullPool)
_PGSession = async_sessionmaker(_PG_ENGINE, expire_on_commit=False)
_db.engine = _PG_ENGINE
_db.AsyncSessionLocal = _PGSession

# Step 4: 此后 import src.main 时，路由中 get_db() 会引用已更新的 _db.AsyncSessionLocal
from src.main import app
```

**NullPool 的作用**：禁用连接池，每次操作独立连接，避免 asyncpg 连接池与 pytest 事件循环的并发冲突（测试结束时不会因池中未释放连接而报错）。

### 4.3 pgvector 扩展初始化

```python
@pytest.fixture(scope="session", autouse=True)
async def setup_db():
    async with _PG_ENGINE.begin() as conn:
        await conn.execute(text("CREATE EXTENSION IF NOT EXISTS vector"))  # pgvector
        await conn.run_sync(Base.metadata.create_all)                      # 建表
        for table in reversed(Base.metadata.sorted_tables):               # 清空上次数据
            await conn.execute(table.delete())
    yield
    # 不 drop tables，schema 保留，数据可事后检查
```

`reversed(sorted_tables)` 按 FK 依赖逆序删除，避免外键约束冲突。

## 5. 如何判断哪些模块需要测试

### 5.1 原则：路由模块对等覆盖

每个 FastAPI router 文件对应一个集成测试文件，测试关注"HTTP 请求→数据库→响应"这条完整链路，而非函数内部实现：

| 测试文件 | 对应 API 模块 | 测试关注点 |
|---------|------------|-----------|
| `test_01_auth.py` | `auth.py` | 注册/登录/JWT 格式/权限隔离 |
| `test_02_goals.py` | `goals.py` | CRUD 完整性/进度计算/跨用户隔离 |
| `test_03_tasks_plans.py` | `tasks.py` + `plans.py` + `schedule.py` | 批量创建/完成状态/日程 upsert |
| `test_04_checkin_debts.py` | `checkin.py` + `debts.py` | 三种打卡模式/债务生命周期 |
| `test_05_knowledge.py` | `knowledge.py` | 文件上传/KB 管理/关键词检索 |
| `test_06_agent.py` | `agent.py` | 宏观计划生成/日报/掌握度验证（真实 LLM） |
| `test_07_notifications.py` | `notifications.py` | 通知增删/标记已读 |
| `test_08_schedule.py` | `schedule.py` | 时间块保存/跨用户隔离 |

### 5.2 选择集成测试而非单元测试的判断标准

- **有 pgvector 依赖** → 必须集成测试（`test_05_knowledge` 的向量检索部分）
- **有跨表状态积累** → 优先集成测试（`test_04` 的连续打卡天数、债务生成）
- **有真实 LLM 调用** → 集成测试，但用 `skipif` 保护（`test_06_agent`，检测 `SMART_API_KEY`）
- **纯输入/输出校验** → 单元测试即可（参数校验、错误码）

## 6. 测试方法详解

### 6.1 标准测试结构

```python
# 所有集成测试都标记 pytestmark
pytestmark = pytest.mark.integration

# 使用 session 级 fixture：client, auth_headers, shared, seed
async def test_create_goal_exam(
    client: AsyncClient,
    auth_headers: dict,
    shared: dict,
    seed: dict,
):
    r = await client.post(
        "/api/v1/goals",
        json=seed["goals"][0],        # 从固定 seed 数据读取，避免硬编码
        headers=auth_headers,
    )
    assert r.status_code == 201, r.text          # 先断言状态码（r.text 是失败时的调试信息）
    data = r.json()
    assert data["type"] == "exam"
    assert data["title"] == seed["goals"][0]["title"]
    shared["goal_id_1"] = data["id"]              # 写入共享状态
```

### 6.2 权限隔离测试模式

注册两个用户（`seed["user"]` 和 `seed["user2"]`），验证数据不泄露：

```python
async def test_other_user_cannot_access(client, shared, seed):
    # user2 的 token
    r = await client.post("/api/v1/auth/login",
        json={"email": seed["user2"]["email"], "password": seed["user2"]["password"]})
    other_headers = {"Authorization": f"Bearer {r.json()['access_token']}"}

    # user2 不能访问 user1 的目标
    r = await client.get(f"/api/v1/goals/{shared['goal_id_1']}", headers=other_headers)
    assert r.status_code == 404    # 不是 403，防止信息泄露
```

### 6.3 LLM 调用的跳过保护

真实 API 调用受环境变量保护，不影响 CI 环境运行：

```python
HAS_LLM = bool(os.getenv("SMART_API_KEY") and os.getenv("SMART_API_KEY") not in ("", "test"))

async def test_macro_plan_generate(client, auth_headers, shared):
    if not HAS_LLM:
        pytest.skip("未配置 SMART_API_KEY，跳过 LLM 测试")
    r = await client.post(f"/api/v1/agent/macro-plan/{shared['goal_id_1']}", headers=auth_headers)
    assert r.status_code == 200
    data = r.json()
    assert "phases" in data
    assert len(data["phases"]) >= 2    # 验证输出结构，不验证内容（LLM 输出不确定）
```

### 6.4 seed_data.json：固定输入集

所有测试输入从 `fixtures/seed_data.json` 读取，避免测试代码中硬编码字符串：

```json
{
  "user": { "email": "integration@planpilot.dev", "username": "int_tester", "password": "IntTest@2026" },
  "goals": [
    { "type": "exam", "title": "CPA备考2026", "deadline": "2026-12-31", "daily_hours": 2.0, ... },
    { "type": "skill", "title": "Python编程技能", "deadline": "2026-10-31", ... }
  ],
  "tasks": [ ... ],
  "checkins": [ ... ],
  "knowledge_texts": [ ... ]
}
```

好处：修改测试数据只改 JSON，不改测试代码；同一份数据在多个测试文件中复用。

## 7. 测试计时与 HTML 报告生成

### 7.1 计时来源

pytest 内置计时器在每个测试函数执行前后打点，记录：
- 每个测试的耗时（显示在 `-v` 输出的每行末尾）
- 总耗时（最终汇总行：`55 passed in 52.40s`）

Session 级 fixture 的初始化时间（建连、建表、清数据）计入第一个测试的耗时，因此 `test_01_auth::test_register_success` 耗时会略长于其他测试。

### 7.2 pytest-html 插件工作原理

pytest-html 通过 pytest 的钩子系统收集运行数据：

```
pytest 执行时：
  pytest_runtest_logreport(report) → 每个测试完成时回调
    → 收集：测试名、状态、耗时、捕获的 stdout/stderr、异常堆栈
  pytest_sessionfinish() → 所有测试完成后回调
    → 渲染 Jinja2 模板 → 输出 HTML
```

`--self-contained-html` 参数让 CSS/JS 内嵌到 HTML 文件，无需 CDN，单文件可直接在浏览器打开。

### 7.3 报告生成命令

`run_integration_tests.sh` 中：

```bash
TIMESTAMP=$(date +%Y%m%d_%H%M%S)    # 时间戳避免覆盖历史报告

pytest tests/integration/ \
    --html="tests/integration/reports/report_${TIMESTAMP}.html" \
    --self-contained-html \
    -m integration \                  # 只运行标记了 @pytest.mark.integration 的测试
    -v \                              # 逐行打印测试名+结果
    --tb=short                        # 失败时显示简短堆栈
```

### 7.4 test_data_snapshot.json

测试结束时，`shared` fixture 的 teardown 阶段将整个共享状态 dict 写入 JSON：

```python
@pytest.fixture(scope="session")
def shared():
    state = {}
    yield state
    # session 结束时执行
    snapshot_path = REPORTS_DIR / "test_data_snapshot.json"
    snapshot_path.write_text(json.dumps(state, indent=2, ensure_ascii=False))
```

输出示例：
```json
{
  "user": { "id": "abc123", "email": "integration@planpilot.dev" },
  "goal_id_1": "d1e2f3...",
  "goal_id_2": "a4b5c6...",
  "task_ids": ["t1...", "t2...", "t3..."],
  "kb_id": "k7l8m9...",
  "plan_id": "p0q1r2..."
}
```

用途：事后在 psql 中查询验证数据是否真实写入，如：

```sql
SELECT COUNT(*) FROM goals WHERE id = 'd1e2f3...';
SELECT * FROM checkin_records ORDER BY created_at;
```

## 8. 运行指南

### 8.1 前置条件

```bash
# 1. PostgreSQL 已运行，创建测试库
createdb planpilot_test

# 2. 安装测试依赖
pip install -r backend/requirements-test.txt

# 3. 如需测试 LLM 链路，确保 .env 中有 SMART_API_KEY
```

### 8.2 运行方式

```bash
# 完整运行（推荐，含 HTML 报告 + 自动打开浏览器）
bash backend/run_integration_tests.sh

# 只运行特定模块
bash backend/run_integration_tests.sh tests/integration/test_01_auth.py

# 运行时跳过 LLM 测试（不配置 SMART_API_KEY 即可，LLM 测试自动 skip）
```

### 8.3 测试产物

| 文件 | 内容 |
|------|------|
| `tests/integration/reports/report_YYYYMMDD_HHMMSS.html` | 可视化 HTML 报告，浏览器可打开 |
| `tests/integration/reports/test_data_snapshot.json` | 本次测试创建的所有资源 ID |

### 8.4 数据清理

集成测试默认**不清理数据**（便于事后验证）。如需重置：

```bash
psql planpilot_test -c "
  TRUNCATE checkin_records, tasks, plans, goals, knowledge_items,
           knowledge_bases, daily_schedules, daily_brief_caches,
           users CASCADE;
"
```

或直接删库重建：

```bash
dropdb planpilot_test && createdb planpilot_test
```
