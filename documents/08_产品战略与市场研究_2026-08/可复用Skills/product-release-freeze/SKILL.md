# 产品发布评估与冻结

用当前代码、真实运行环境和实际发行产物判断产品是否可以交付。历史测试、文档声明、源码能够构建或开发环境可用，都不能单独证明发布就绪。

执行具体项目验收时，读取 [发布验收矩阵](references/发布验收矩阵.md)，只使用与当前发行类型相关的部分。

## 明确发行目标

先确认本次判断针对哪一级目标：

- 内部预览：供开发者或小范围团队体验，允许明确配置步骤和已知限制。
- 内部 Beta：核心用户路径稳定，可恢复，已知问题不会阻断主要目标。
- 外部 Beta：陌生用户可以安装、首次启动、理解边界并获得支持。
- 公开发行：具备稳定基线、安全与隐私保障、升级路径、分发合规和持续维护能力。

如果用户未指定，基于当前语境选取最合理目标，并明确说明。不要用较低级别通过冒充更高级别就绪。

## 保持授权边界

完成度评估、审查和冻结规划默认是只读工作。除非用户明确要求，不要：

- 修改实现或测试。
- 提交、打标签或推送代码。
- 构建并发布正式安装包。
- 签名、公证、上传、部署或通知外部人员。
- 删除数据、卷、缓存或旧产物。

可以执行安全、可逆且与判断直接相关的读取、构建和测试。高成本、影响运行环境或可能改变数据的验证应先确认范围并使用隔离环境。

## 建立当前基线

1. 记录仓库、分支、提交、工作区状态和相关子项目。
2. 确认被测试的服务、页面或安装包确实来自该基线。
3. 区分当前运行结果、历史报告和文档中的计划值。
4. 记录环境、端口、平台、架构、配置模式和外部依赖。
5. 检查未提交改动、未跟踪文件、生成物和秘密信息风险。

工作区不干净不必自动判定产品不可用，但不能宣称已有可复现、可冻结的发布基线。

## 六条评估通道

### 1. 产品闭环

- 核心用户是谁，主要目标是什么？
- 首次进入、主任务、成功反馈、失败恢复和再次进入是否完整？
- 空状态、权限、数据保留和退出路径是否可理解？
- 是否把内部架构、手动配置或技术步骤转嫁给目标用户？

### 2. 工程质量

- 类型检查、静态检查、生产构建和关键测试是否基于当前代码通过？
- 实现与测试契约是否漂移？
- 失败是产品回归、测试陈旧、环境问题还是偶发超时？
- 是否存在共享外壳、认证、数据迁移或关键依赖的系统性风险？

### 3. 真实运行

- 前端、API、数据库、队列、缓存、存储和模型依赖是否健康？
- 冷启动、停止、重启、恢复和离线/弱网边界是否符合发行承诺？
- 当前页面是否来自预期源码和配置？
- 关键链路是否在目标环境真实走通，而不只是单元测试通过？

### 4. 安装与分发

- 实际安装包能否在目标设备打开？
- 首次启动是否需要目标用户无法完成的准备？
- 默认窗口、最小尺寸、图标、名称、权限提示和卸载行为是否合理？
- 安装包中的资源是否与冻结提交一致？

### 5. 数据、安全与升级

- 密钥、隐私数据、上传内容、日志和备份是否受到保护？
- 权限、远程地址、明文通信和破坏性操作是否有明确边界？
- 升级是否复用正确数据与密钥，迁移失败是否可恢复？
- 本地与云端模式的数据归属和同步承诺是否真实？

### 6. 运营与维护

- 已知限制、支持方式、监控、回滚、备份和恢复是否与发行级别匹配？
- 是否存在明确负责人、版本标识和问题追踪入口？
- 对外发行所需的许可证、签名、公证、隐私说明和更新机制是否完成？

## 选择验证强度

先运行能最快暴露阻塞的定向门禁，再决定是否扩大验证：

- 普通 Web 迭代：生产构建、核心路由、关键 E2E、后端健康。
- 数据或 Agent 变化：真实数据库、权限、迁移、幂等、失败恢复和关键评估门禁。
- 桌面应用：安装包本体、首次启动、再次启动、窗口行为、本地/远程连接和退出恢复。
- 本地一体化运行时：冷镜像导入、全服务健康、端口隔离、数据卷保留和升级恢复。

验证产物而不只是源码。用户明确要求跳过某类测试时遵循要求，并把未验证部分计入置信度和剩余风险。

## 做发布判断

使用明确结论：

- **Go**：目标发行级别的关键路径和阻塞门禁均有当前证据支持。
- **Conditional Go**：可以限定人群或用途交付，但必须清楚列出条件、监控和回退方式。
- **No-Go**：存在阻断核心目标、数据安全、安装启动、恢复或可复现基线的问题。

完成度百分比只能作为辅助。使用时分别评估产品功能、工程质量、运行准备、分发准备和运营准备，说明依据与置信度，不把主观估计伪装成精确测量。

## 冻结发布基线

只有用户授权冻结，并且所需条件满足时才执行：

1. 确认目标仓库和工作区状态。
2. 记录确切提交、依赖锁定、配置模式和构建环境。
3. 保存当前测试结果，区分通过、失败、跳过与未运行。
4. 生成或确认发行产物，并验证产物来自冻结基线。
5. 记录产物路径、大小、平台、架构和校验信息（适用时）。
6. 写明已知限制、阻塞、回退方式和下一版本入口。
7. 提交、打标签、签名、公证、上传或部署仍分别需要对应授权。

## 输出格式

最终报告应先给结论，再给证据：

1. 目标发行级别与 Go/Conditional Go/No-Go。
2. 各通道完成度和最高风险。
3. 当前验证结果及其基线。
4. 阻塞项、非阻塞已知问题和未验证部分。
5. 可以交付的实际产物。
6. 达到下一发行级别所需的最短行动清单。

不要用大量测试通过掩盖一个关键阻塞，也不要把旧报告中的绿色结果描述为当前验证。
