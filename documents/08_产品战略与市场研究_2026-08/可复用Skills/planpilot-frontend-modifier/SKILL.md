# 修改 PlanPilot 产品前端

所有前端工作都以当前真实产品为准，不依据记忆、旧截图或归档版本实施。真实渲染行为和视觉证据是最终验收面。

## 加载项目上下文

1. 阅读 `frontend/README.md` 和用户明确提到的文件。
2. 选择路由、样式表、变量或测试前，阅读 [项目地图](references/项目地图.md)。
3. 阅读 [设计与交互偏好](references/设计与交互偏好.md)。
4. 检查 `git status --short`，保留无关的既有修改。
5. 用户提供截图时，在编辑前查看全部图片，并区分结构要求与风格参考。

## 编辑前理解产品语义

形成简短的内部验收清单：

- 确认受影响的页面、对象、操作和范围。
- 区分主要内容、次要信息、交互控件、状态展示和破坏性操作。
- 判断操作属于页面、选中对象、目标还是全局外壳。
- 区分用户明确要求与可选建议；不要因为另一功能看似重复就删除明确要求。
- 用户描述“现在看到的效果”时，检查当前渲染结果或现有测试。

当用户要求“先理解再做”，或产品语义会决定布局时，用简短评论说明理解；除非缺失决策会实质改变结果，否则继续实施。

## 找到真实实现层

1. 从 `frontend/` 使用 `rg` 搜索，不假设旧选择器、路由或组件仍在生效。
2. 按 `app/(technology)/studio/layout.tsx` 中的导入顺序追踪样式层叠。
3. 新增覆盖前检查后置选择器、特异性、媒体查询、主题属性和内联样式。
4. 用户要求与其他 PlanPilot 页面一致时，复用已有组件、令牌、标题卡、标签、按钮和页面几何，不凭肉眼近似。
5. 全局规则覆盖包装节点时，修改真实文本或控件节点，并在编辑后检查计算样式。
6. TSX 承载结构，共享视觉规则放入范围最窄的现有样式表；不要在无关 CSS 文件末尾持续堆积临时覆盖。

## 设计修改

按以下顺序决策：

1. 保留任务流程和产品含义。
2. 通过内容顺序、字体、间距和对比建立层级。
3. 减少多余容器和装饰。
4. 让控件靠近它影响的值或对象。
5. 保留主题和响应式行为。
6. 仅在动效能够解释状态或交互时添加动效。

优先保留一个明确主操作。证据、进阶设置和 AI 推理使用渐进披露。相邻页面采用固定工作区底部时，长列表应使用有边界的内部滚动区域。

## 安全实施

- 保留 React、TypeScript、可访问性语义、键盘焦点、减少动态效果偏好和现有数据流。
- 主题通过令牌、材质与强调色表达，不在主题间改变布局、信息架构或内容顺序。
- 语义色保持一致：红色用于错误和破坏性操作，成功、警告、交互、禁用与正文角色应清晰区分。
- 视觉上缩小图标或胶囊时，仍保留足够的可点击区域。
- 被修改的异步流程需要时，补齐空、加载、保存中、成功、失败和重试状态。
- AI 或 Pilo 修改任务、日期、计划、笔记、目标或学习者记忆前，展示预览并要求确认。
- 不用可点击的假控件伪装尚未工作的后端功能；明确偏好是仅本地保存还是已同步。
- Pilo 与内容发生视觉重叠时，按项目约定视为有意产品行为，不以此为理由修改 Pilo、层级、位置或周边布局。只有用户明确提出非重叠原因的 Pilo 修改时才调整。

## 验证结果

验证强度与改动风险相称，但视觉改动不得跳过真实渲染检查，除非用户明确要求不测试。

1. 运行有针对性的 TypeScript 与 ESLint 检查。
2. 运行最近的 Playwright 测试；对易回归的新行为补充聚焦测试。
3. 从 `frontend/playwright.config.ts` 或当前进程确认正确开发地址，避免检查旧 Docker 或旧 Next.js 实例。
4. 用户可见界面检查目标桌面宽度和 375px 窄屏。
5. 检查对齐、层级、裁切、溢出、滚动边界、焦点、悬停、展开/收起状态和受影响的主题变体。
6. 精确字号、间距和对齐请求使用计算样式或元素几何确认，不根据 CSS 源码推断视觉成功。
7. 跨路由、主题或共享外壳修改在可行时运行生产构建。

页面陈旧时先确认活动端口与源码。只有证据指向缓存时才清理 `.next` 或重启服务；不要用清缓存代替修复样式问题。

## 如实交付

先说明改动结果，再说明确切行为、涉及文件、执行过的验证和必要时的当前 URL。重大视觉改动提供截图。区分新失败与既有失败；未查看真实渲染结果时不得宣称视觉完成。
